# Skill: wrap-up

> This skill cleans up feature branches after all MRs are merged, publish comprehensive Confluence documentation, post a coding summary to JIRA, and transition the issue to Complete.

---

## Purpose

This skill performs post-merge wrap-up for a JIRA feature issue. It verifies that all Merge Requests across impacted projects have been merged, deletes the corresponding feature branches (local and remote), **publishes comprehensive functional and technical documentation to Confluence** under a configurable parent page (mandatory — every feature must have a Confluence page), posts a comprehensive coding summary comment to the JIRA issue in wiki markup, and transitions the issue to "Complete" or "Done". Knowledge base integration (AGENTS.md, knowledge specs, LEARNINGS.md) is handled separately by the `/sdd-update-knowledge` skill.

**Note:** The per-feature change summary (`ai/specs/{ISSUE_ID}/change-summary.md`) is generated by the `/sdd-execute` skill and includes the traceability matrix, task progress checklist, modules affected, files modified, and test results. The `wrap-up` skill references this artifact but does not regenerate it.

**This skill does NOT merge anything.** All MRs must already be in the `merged` state before running this skill. If any MR is still open, the skill stops immediately.

---

## Prerequisites

- `local.config` at workspace root contains `JIRA_PAT` and `GIT_PAT`:
  ```
  JIRA_PAT=<Base64-encoded JIRA personal access token>
  GIT_PAT=<GitLab personal access token (glpat-...)>
  ```
- `local.config` must also contain Confluence credentials for publishing documentation:
  ```
  CONFLUENCE_PAT=<Base64-encoded Confluence personal access token>
  CONFLUENCE_PARENT=<Full URL of the parent Confluence page>
  ```
  If either `CONFLUENCE_PAT` or `CONFLUENCE_PARENT` is missing or empty, the skill will **warn the user and prompt for configuration** before proceeding — Confluence documentation is a mandatory deliverable.
- Each git project has an `origin` remote pointing to a GitLab instance (derived dynamically from the remote URL).
- Feature branches follow the naming convention `develop-PROJECT-XXXX` (where `PROJECT-XXXX` is the JIRA issue ID).
- All Merge Requests for the feature must already be merged into `develop`.
- The JIRA issue exists and is accessible with the configured `JIRA_PAT`.

## Skill Steps

### Step 1 — Obtain JIRA Issue ID

Determine the JIRA issue ID (`PROJECT-XXXX`) for this feature. Sources (in priority order):

1. The user provides it directly (e.g., "wrap up PROJECT-1234").
2. Detect from the current branch name: `git branch --show-current` → `develop-PROJECT-1234` → extract `PROJECT-1234`.
3. Prompt the user if it cannot be determined.

Store as `ISSUE_ID` (e.g., `PROJECT-1234`). The feature branch name pattern is `develop-{ISSUE_ID}` (e.g., `develop-PROJECT-1234`).

#### Step 1A — Resolve Spec / Story Relationship

Resolve the Spec/Story relationship for dual-update during wrap-up:

1. Fetch the issue: `jira_get_issue` with `fields: issuetype,issuelinks`
2. If `issuetype.name` is `Story`:
   - Invoke `/sdd-story-to-spec` with the Story ID to get or create a linked Spec.
   - The Spec ID returned becomes the new `{ISSUE_ID}` for all downstream steps.
   - Record the original Story ID as `{LINKED_STORY_ID}`.
3. If `issuetype.name` is `Spec`:
   - Scan `issuelinks` for a linked Story. Record as `{LINKED_STORY_ID}` (or null if none).
4. For any other issue type:
   - Scan `issuelinks` for a linked Spec. If found, switch to the Spec as `{ISSUE_ID}`.
   - Scan for a linked Story. Record as `{LINKED_STORY_ID}` (or null if none).
5. Record `{LINKED_STORY_ID}` for dual-update at Steps 6, 6.3, and 7.

> **Note:** The feature branch name `develop-{ISSUE_ID}` may reference either the original Story ID or the Spec ID. Step 3 (MR verification) and Step 4 (branch deletion) must check for branches matching **both** IDs when `{LINKED_STORY_ID}` is set.

### Step 2 — Load Authentication

Read credentials from the workspace-root `local.config` file:

```bash
# WORKSPACE_ROOT should already be set; if not, use the current working directory
WORKSPACE_ROOT="${WORKSPACE_ROOT:-$(pwd)}"
JIRA_PAT=$(grep JIRA_PAT "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
GIT_PAT=$(grep GIT_PAT "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
CONFLUENCE_PAT=$(grep CONFLUENCE_PAT "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
CONFLUENCE_PARENT=$(grep CONFLUENCE_PARENT "$WORKSPACE_ROOT/local.config" | cut -d= -f2-)
JIRA_BASE_URL=$(grep JIRA_BASE_URL "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
CONFLUENCE_BASE_URL=$(grep CONFLUENCE_BASE_URL "$WORKSPACE_ROOT/local.config" | cut -d= -f2-)
```

**JIRA API auth** uses the PAT as a Bearer token:
```
Authorization: Bearer $JIRA_PAT
```

**GitLab API auth** uses the PAT as a private token header:
```
PRIVATE-TOKEN: $GIT_PAT
```

**Confluence API auth** uses the PAT as a Bearer token:
```
Authorization: Bearer $CONFLUENCE_PAT
```

**Base URLs:**
- JIRA: Read `JIRA_BASE_URL` from `local.config`
- GitLab: Derive from the project's `origin` remote URL
- Confluence: Read `CONFLUENCE_BASE_URL` from `local.config` (optional)

### Step 3 — Verify All MRs Are Merged (Two-Phase for Submodules)

Before deleting any branches, verify that every submodule's MR and the parent ai/ repo MR are safely merged. **Do NOT proceed if any MR is still open.**

**Two-Phase Merge Strategy:**
1. **Phase 1:** Verify all submodule MRs are merged
2. **Phase 2:** After submodule refs are updated, verify parent ai/ repo MR is merged

**Git projects to check** — dynamically discover:
1. All submodules under `ai/submodules/`
2. The parent `ai/` repository

For submodules:
1. Iterate over every subdirectory under `ai/submodules/`.
2. For each submodule, check if it contains a `.git` directory.
3. Determine the GitLab project path by reading the `origin` remote URL.

For the parent ai/ repo:
1. Check the `ai/` directory itself.
2. Determine its GitLab project path.

```bash
REMOTE_URL=$(git remote get-url origin)
# Derive GitLab host and API base from the remote URL
GIT_HOST=$(echo "$REMOTE_URL" | sed 's|https://\([^/]*\)/.*|\1|')
GIT_API_BASE="https://${GIT_HOST}/api/v4"
# Extract path: remove https://<host>/ prefix and .git suffix
PROJECT_PATH=$(echo "$REMOTE_URL" | sed 's|https://[^/]*/||; s|\.git$||')
# URL-encode: replace / with %2F
ENCODED_PATH=$(echo "$PROJECT_PATH" | sed 's|/|%2F|g')
```

#### 3.1 — Phase 1: Verify Submodule MRs

For each submodule under `ai/submodules/`:

```bash
cd ai/submodules/<submodule-name>
git fetch origin
git branch -r --list "origin/develop-${ISSUE_ID}"
```

Check MR status via GitLab API:

```bash
# Query for merged MRs
curl -s --header "PRIVATE-TOKEN: $GIT_PAT" \
  "${GIT_API_BASE}/projects/<ENCODED_PATH>/merge_requests?source_branch=develop-${ISSUE_ID}&target_branch=develop&state=merged"

# Query for opened MRs
curl -s --header "PRIVATE-TOKEN: $GIT_PAT" \
  "${GIT_API_BASE}/projects/<ENCODED_PATH>/merge_requests?source_branch=develop-${ISSUE_ID}&target_branch=develop&state=opened"
```

#### 3.2 — Phase 2: Update Parent Repo Submodule References

After all submodule MRs are verified as merged:

1. **Update submodule refs in parent ai/ repo:**
```bash
cd ai
git checkout develop-${ISSUE_ID}
git submodule update --remote --merge
git add ai/submodules/*
git commit -m "JIRA#{ISSUE_ID}; Update submodule refs after merge: <list-of-submodules>"
git push origin develop-${ISSUE_ID}
```

2. **Verify parent ai/ repo MR status:**
```bash
cd ai
# Check MR status
curl -s --header "PRIVATE-TOKEN: $GIT_PAT" \
  "${GIT_API_BASE}/projects/<AI_ENCODED_PATH>/merge_requests?source_branch=develop-${ISSUE_ID}&target_branch=develop&state=merged"
```

#### 3.3 — Classification Rules

**For submodules:**
|| Remote branch? | MR state | Local branch? | Classification | Action |
||---|---|---|---|---|
|| Yes/No | `merged` | Yes/No | **Safe** | Proceed with branch deletion |
|| Yes/No | `opened` | Yes/No | **STOP** | Halt entire skill — MR must be merged first |
|| Yes | No MR found | Yes/No | **Warn** | Remote branch exists but no MR — ask user to confirm deletion |
|| No | No MR found | Yes | **Safe** | Only local branch remains — safe to delete |
|| No | No MR found | No | **Skip** | No involvement with this feature — nothing to do |

**For parent ai/ repo:**
|| Submodule refs updated? | MR state | Local branch? | Classification | Action |
||---|---|---|---|---|
|| Yes | `merged` | Yes/No | **Safe** | Proceed with branch deletion |
|| No | `opened` | Yes/No | **STOP** | Update refs first, then verify MR merged |
|| No | No MR found | Yes | **Warn** | No MR found — ask user to confirm deletion |

#### 3.4 — Present Two-Phase Summary

Display a table summarizing all submodules and parent repo:

```
=== Two-Phase MR Verification Summary for {ISSUE_ID} ===

Phase 1: Submodules
|| Submodule            | Remote Branch | Local Branch | MR Status | Classification |
||----------------------|---------------|--------------|-----------|----------------|
|| ai/submodules/project-alpha | YES | YES | merged | Safe |
|| ai/submodules/project-beta  | YES | YES | merged | Safe |

Phase 2: Parent Repo
|| Repo    | Submodule Refs Updated | MR Status | Local Branch | Classification |
||---------|------------------------|-----------|--------------|----------------|
|| ai      | YES                    | merged    | YES          | Safe |
```

**If any submodule has classification = STOP**, halt the entire skill and report which MRs are still open.

**If parent ai/ repo has classification = STOP**, run the ref update step (3.2) and re-verify the MR status.

### Step 4 — Delete Feature Branches

For each project classified as **Safe** or **Warn (confirmed)**, perform branch cleanup:

#### 4.1 — Switch to develop

```bash
cd <project-dir>
git checkout develop && git pull origin develop
```

**Error handling:** If `git checkout develop` fails (e.g., uncommitted changes):
```bash
git fetch origin develop
git checkout -f develop
git reset --hard origin/develop
```

#### 4.2 — Delete local feature branch

```bash
git branch -D develop-${ISSUE_ID}
```

**Error handling:**
- If the branch does not exist locally, that's fine — skip.
- If `-D` fails because it's "not fully merged" — this should NOT happen since we verified the MR is merged. **STOP and report** this anomaly. Do not force-delete without investigation.

#### 4.3 — Delete remote feature branch (if it exists)

```bash
git push origin --delete develop-${ISSUE_ID}
```

**Error handling:**
- If the remote branch was already deleted (error: `remote ref does not exist`) — that's fine, continue.
- If there's a permission error (403) — report the failure but continue with other projects. The user may need to delete it manually via GitLab UI.

#### 4.4 — Prune stale remote-tracking references

```bash
git fetch --prune
```

This removes any remaining `origin/develop-{ISSUE_ID}` remote-tracking references.

### Step 5 — Gather Coding Summary

Collect information for the JIRA summary comment from multiple sources:

#### 5.1 — Feature specification

If a feature spec exists at `ai/specs/{ISSUE_ID}/specs.md`, read it **in full** to extract:
- **Overview** (§4.2) — business summary of what the feature does and why it matters
- **Background & Context** (§4.3) — business problem, JIRA description, app spec references
- **Scope** (§4.4) — in-scope deliverables and out-of-scope exclusions
- **Functional Requirements** (§4.5) — numbered requirements table (ID | Requirement | Source)
- **Acceptance Criteria** (§4.6) — Given/When/Then or checklist format
- **Non-Functional Requirements** (§4.7) — performance, security, scalability, compatibility constraints
- **Impacted Areas** (§4.8) — table of areas, files/classes/endpoints, nature of change
- **Open Questions & Assumptions** (§4.9) — resolved questions and standing assumptions

#### 5.2 — Implementation plan

If an implementation plan exists at `ai/specs/{ISSUE_ID}/plan.md`, read it **in full** to extract:
- **Context** (§5.2) — technical approach, API endpoints involved, key technical challenges
- **Example Request & Response** (§5.2.1) — sample API payloads if applicable
- **Feature-Specific Logic** (§5.2.2) — business rules, merge strategies, routing logic, event schemas
- **Files to Modify** (§5.2.4) — detailed file list with paths, methods, and change descriptions
- **Files NOT to Modify** (§5.2.5) — explicit exclusions with reasoning
- **Implementation Order** (§5.2.6) — TDD steps, test case names and descriptions
- **Critical Constraints** (§5.2.7) — backward compatibility, reactive, atomicity, signing requirements
- **Key Code References** (§5.4) — reference table of files, methods, and line numbers

#### 5.3 — Git log for commits

For each project that had a merged MR, collect commits referencing this issue:

```bash
cd <project-dir>
git fetch origin develop
git log origin/develop --oneline --grep="JIRA#${ISSUE_ID}"
```

Also try alternative patterns:
```bash
git log origin/develop --oneline --grep="${ISSUE_ID}"
```

Record: commit hash, one-line message, author, date.

#### 5.4 — GitLab MR details

For each merged MR, fetch full details:

```bash
curl -s --header "PRIVATE-TOKEN: $GIT_PAT" \
  "${GIT_API_BASE}/projects/<ENCODED_PATH>/merge_requests?source_branch=develop-${ISSUE_ID}&target_branch=develop&state=merged"
```

Extract per MR:
- MR IID and title
- MR web URL
- Author
- Merge date (`merged_at`)
- Number of changes (files modified)

Fetch MR changes to get the list of files modified:

```bash
curl -s --header "PRIVATE-TOKEN: $GIT_PAT" \
  "${GIT_API_BASE}/projects/<ENCODED_PATH>/merge_requests/<MR_IID>/changes"
```

Extract from `changes[]`:
- File paths (`new_path`)
- Change type (added, modified, deleted — infer from `new_file`, `deleted_file`, `renamed_file` flags)

#### 5.5 — Test information

Note any test classes added or modified from the MR changes list (files matching `*Test.java`, `*Tests.java`, `*Spec.java`, `*IT.java`).

### Step 6 — Post Summary Comment to JIRA

Compose a JIRA comment in **wiki markup** and post it to the issue.

#### 6.1 — Wiki markup template

```
{panel:title=Feature Complete — {ISSUE_ID}|borderStyle=solid|borderColor=#00875a|titleBGColor=#00875a|titleColor=#ffffff|bgColor=#f0fff0}

h3. Summary

{summary_text}

h3. Merge Requests

||||Project||MR||Title||Author||Merged||Files Changed||
|||{project_1}|[!{mr_iid_1}|{mr_url_1}]|{mr_title_1}|{mr_author_1}|{merged_date_1}|{file_count_1}|
|||{project_2}|[!{mr_iid_2}|{mr_url_2}]|{mr_title_2}|{mr_author_2}|{merged_date_2}|{file_count_2}|

h3. Files Modified

||||Project||File||Change Type||
|||{project}|{{file_path_1}}|Modified|
|||{project}|{{file_path_2}}|Added|
|||{project}|{{file_path_3}}|Deleted|

h3. Tests

||||Project||Test Class||Type||
|||{project}|{{TestClassName1}}|Unit|
|||{project}|{{TestClassName2}}|Integration|

h3. Commits

||||Project||Hash||Message||
|||{project_1}|{{abc1234}}|{commit_message_1}|
|||{project_1}|{{def5678}}|{commit_message_2}|
|||{project_2}|{{ghi9012}}|{commit_message_3}|

h3. Artifacts Retained

* Feature spec: {{ai/specs/{ISSUE_ID}/specs.md}}
* Implementation plan: {{ai/specs/{ISSUE_ID}/plan.md}}
* Session logs retained in {{.devin/}} workspace directory

{panel}
```

**Substitution rules:**
- `{summary_text}` — 2–4 sentence summary of what was implemented, derived from the feature spec and MR titles.
- `{mr_url_N}` — Full GitLab web URL for the MR (e.g., `https://{git-host}/{project-path}/-/merge_requests/{id}`).
- `{merged_date_N}` — Format as `YYYY-MM-DD`.
- `{file_count_N}` — Number of files in the MR's `changes[]` array.
- Test type: infer `Integration` if file name contains `IT`, otherwise `Unit`.

#### 6.2 — Post the comment

**Primary Method: Use MCP Tool**

```
mcp2_jira_add_comment
  issue_key: {ISSUE_ID}
  body: {wiki_markup_content}
```

**Curl Fallback Method**

Use curl when MCP fails or is unavailable:

```bash
# Get configuration
JIRA_PAT=$(grep JIRA_PAT "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
JIRA_BASE_URL=$(grep JIRA_BASE_URL "$WORKSPACE_ROOT/local.config" | cut -d= -f2)

# Post the comment
curl -s --request POST \
  --header "Authorization: Bearer $JIRA_PAT" \
  --header "Content-Type: application/json" \
  --data '{
    "body": "'${WIKI_MARKUP_CONTENT}'"
  }' \
  "${JIRA_BASE_URL}/rest/api/2/issue/${ISSUE_ID}/comment"
```

**Error handling:**
- Success — Comment posted successfully.
- Authentication failure — Report but do NOT fail the skill. Branch cleanup is already done.
- Issue not found — Report.
- Network error — Report but do NOT fail the skill.
The MCP tool handles authentication automatically.

#### 6.3 — Add `AI-Delivered` label

**Primary Method: Use MCP Tool**

```
mcp2_jira_add_comment
  issue_key: {ISSUE_ID}
  body: |
    {panel:title=Label Added|borderStyle=solid|borderColor=#0052cc|titleBGColor=#deebff|bgColor=#f0f8ff}
    Added label: *AI-Delivered*
    {panel}
```

**Curl Fallback Method**

```bash
# Get configuration
JIRA_PAT=$(grep JIRA_PAT "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
JIRA_BASE_URL=$(grep JIRA_BASE_URL "$WORKSPACE_ROOT/local.config" | cut -d= -f2)

# Add the label
curl -s --request PUT \
  --header "Authorization: Bearer $JIRA_PAT" \
  --header "Content-Type: application/json" \
  --data '{
    "update": {
      "labels": [{"add": "AI-Delivered"}]
    }
  }' \
  "${JIRA_BASE_URL}/rest/api/2/issue/${ISSUE_ID}"
```

This uses the JIRA `update` field operation to **add** the label without removing any existing labels on the issue.

**Error handling:**
- `204` — Success (no content).
- `200` — Success.
- `401`/`403` — Authentication failure. Report but do NOT fail the skill.
- `404` — Issue not found. Report.
- Network error — Report but do NOT fail the skill.

**JIRA failure is NOT a skill failure.** The primary goal (branch cleanup) has already been achieved by this point.

### Step 7 — Transition JIRA to Complete

Move the JIRA issue to the **"Complete"** status. This is the final state in the SDD lifecycle, indicating deployment is done and the issue is fully closed out.

#### 7.1 — Fetch current issue status

```
mcp2_jira_get_issue
  issue_key: {ISSUE_ID}
  fields: status
```

Check `status.name`. If already "Complete", skip the transition.

#### 7.2 — Get available transitions

**Primary Method: Use MCP Tool**

```
mcp2_jira_get_transitions
  issue_key: {ISSUE_ID}
```

Parse the transitions array. Find a transition where `name` matches (case-insensitive, in priority order):
- `"Complete"` (preferred)
- `"Done"`
- `"Close"`
- `"Resolve"`

Record the transition `id`.

**Curl Fallback Method**

```bash
# Get configuration
JIRA_PAT=$(grep JIRA_PAT "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
JIRA_BASE_URL=$(grep JIRA_BASE_URL "$WORKSPACE_ROOT/local.config" | cut -d= -f2)

# Get available transitions
TRANSITIONS=$(curl -s \
  --header "Authorization: Bearer $JIRA_PAT" \
  "${JIRA_BASE_URL}/rest/api/2/issue/${ISSUE_ID}/transitions")

# Find transition ID for completion status
TRANSITION_ID=$(echo "$TRANSITIONS" | jq -r '.transitions[] | select(.to.name | test("Complete|Done|Close|Resolve"; "i")) | .id' | head -1)
```

#### 7.3 — Execute the transition

**Primary Method: Use MCP Tool**

```
mcp2_jira_transition_issue
  issue_key: {ISSUE_ID}
  transition_id: {TRANSITION_ID}
```

**Curl Fallback Method**

```bash
# Execute transition
curl -s \
  --header "Authorization: Bearer $JIRA_PAT" \
  --header "Content-Type: application/json" \
  -d '{
    "transition": {"id": "'$TRANSITION_ID'"}
  }' \
  "${JIRA_BASE_URL}/rest/api/2/issue/${ISSUE_ID}/transitions"
```

**Error handling:**
- Success — Issue transitioned successfully.
- Permission denied — Report: "Could not transition {ISSUE_ID} — insufficient permissions. Please transition manually."
- No matching transition found — Report: "No 'Complete' or 'Done' transition available from current status '{current_status}'. Please transition manually."
- Network error — Report but do NOT fail the skill.

**JIRA failure is NOT a skill failure.** Branch cleanup has already been completed successfully. The MCP tool handles authentication automatically.

#### 7.4 — Transition Linked Story to Complete (Dual-Update)

**Skip if `{LINKED_STORY_ID}` is null.**

Transition the linked Story to Complete/Done using the same approach as Step 7.1–7.3:

```
mcp2_jira_get_transitions
  issue_key: {LINKED_STORY_ID}
```

Find a matching transition (Complete/Done/Close/Resolve) and execute it:

```
mcp2_jira_transition_issue
  issue_key: {LINKED_STORY_ID}
  transition_id: {STORY_TRANSITION_ID}
```

Story transition is **non-blocking**. If the transition fails (permissions, no matching transition, already complete), log a warning and continue. The Story may require a different transition path — report the skip so the user can handle it manually.

### Step 8 — Commit `ai/` Repo Changes

The `ai/` directory is a separate Git repository. Commit any changes made during this session (e.g. updated specs, change-summary).

**Stage and commit:**

```bash
cd {WORKSPACE_ROOT}/ai
git add -A
git status
```

If there are staged changes, commit them:

```bash
git commit -m "JIRA#${ISSUE_ID}; Post wrap-up sync"
```
(Commit message format defined in `AGENTS.md`)

If there are no changes to commit, skip silently. If the `ai` repo is on `develop` (not a feature branch), push the commit directly.

### Step 9 — Knowledge Integration (deferred to `update-knowledge`)

After a feature is merged, the workspace knowledge base (AGENTS.md, knowledge specs, LEARNINGS.md) should reflect any functional changes introduced. **This is handled by the separate `/sdd-update-knowledge` skill**, which can be run periodically to batch-integrate multiple delivered features.

The `wrap-up` skill does **not** perform knowledge integration inline — it focuses on branch cleanup, Confluence publishing, and JIRA closure. Run `update-knowledge` after wrap-up (or periodically) to keep the knowledge base current.

### Step 10 — Publish Confluence Documentation Page

Create a comprehensive functional and technical documentation page on Confluence under the configured parent page. This page serves as the **canonical reference** for the delivered change — covering business context, functional requirements, architecture, implementation details, testing, and traceability. **This step is mandatory** — every delivered feature must have a Confluence documentation page.

**If Confluence credentials are missing:**

If `CONFLUENCE_PAT` or `CONFLUENCE_PARENT` is missing or empty in `local.config`:

```
=== Confluence Configuration Required ===

Confluence documentation is a mandatory step in the wrap-up skill.
The following configuration is missing from local.config:

  - CONFLUENCE_PAT:    {MISSING / OK}
  - CONFLUENCE_PARENT:  {MISSING / OK}

Please add the missing values to local.config and re-run /sdd-wrap-up,
or provide them now.
```

**WAIT for user response.** If the user provides the values, update `local.config` and proceed. If the user explicitly asks to skip Confluence (e.g., "skip confluence"), log a warning and continue — but note the skip in the final report.

**If the Confluence API is unreachable** after credentials are configured, retry once after 5 seconds. If still unreachable, log a warning and continue — the documentation can be published later by re-running `/sdd-wrap-up`.

#### 10.1 — Parse parent page URL

Extract the **space key** and **parent page ID** from the `CONFLUENCE_PARENT` URL.

The URL follows the pattern: `${CONFLUENCE_BASE_URL}/spaces/{SPACE_KEY}/pages/{PAGE_ID}/{Page+Title}`

```bash
# Example: ${CONFLUENCE_BASE_URL}/spaces/DF/pages/1286841426/FY27+-+DL+Features+Delivery
```

#### 10.4a — Generate the PlantUML sequence diagram for Section 6.2a

The Confluence `plantuml` macro renders PlantUML source into a diagram inline. You **must** generate a meaningful sequence diagram for every feature — it is not optional.

**Data sources** (in priority order):
1. `ai/specs/{ISSUE_ID}/plan.md` — §5.2.3 (processing flow), §5.2.1 (architecture overview)
2. `ai/specs/{ISSUE_ID}/specs.md` — §4.3 (functional flow), §4.4 (business rules)
3. `ai/specs/{ISSUE_ID}/change-summary.md` — actual classes/methods implemented
4. MR diffs gathered in Step 5 — real class names and call chains

**Diagram construction rules:**
1. Use `@startuml` / `@enduml` delimiters.
2. Diagram type must be a **sequence diagram** (`participant`, `->`, `activate`/`deactivate`).
3. Define participants for each distinct layer or component involved: HTTP client, handler/router, service classes, repositories, external systems (databases, message brokers, caches, external APIs).
4. Use real class names from the implementation (e.g., `RegistrationService`, `EntitlementRepository`), not generic placeholders.
5. Model the **primary happy-path flow** end-to-end. Include key branching only if the feature has distinct conditional paths (e.g., "new vs existing registration").
6. Use `activate`/`deactivate` to show processing scope per participant.
7. Use `note over` or `note right` for important business rules or transformations at key steps.
8. Group related steps with `group` or `alt`/`else` blocks where appropriate.
9. Keep the diagram readable — aim for 20–60 lines of PlantUML source. For complex features with multiple distinct flows, use multiple `group` blocks within a single diagram rather than multiple diagrams.
10. Use the `skinparam` block for consistent styling:
```
skinparam sequenceArrowThickness 2

skinparam sequenceParticipant underline
```

```bash
curl -s --header "Authorization: Bearer $CONFLUENCE_PAT" \
```

```bash
EXISTING_PAGE_ID=<extracted id>
CURRENT_VERSION=<extracted version.number>
NEW_VERSION=$((CURRENT_VERSION + 1))

curl -s --request PUT \
  --header "Authorization: Bearer $CONFLUENCE_PAT" \
  --header "Content-Type: application/json" \
  --data '{
    "type": "page",
    "title": "<PAGE_TITLE>",
    "version": {"number": <NEW_VERSION>},
    "body": {
      "storage": {
        "value": "<ESCAPED_HTML_CONTENT>",
        "representation": "storage"
      }
    }
  }' \
  "${CONFLUENCE_BASE_URL}/rest/api/content/${EXISTING_PAGE_ID}"
```

**If the page does not exist — create it:**

```bash
curl -s --request POST \
  --header "Authorization: Bearer $CONFLUENCE_PAT" \
  --header "Content-Type: application/json" \
  --data '{
    "type": "page",
    "title": "<PAGE_TITLE>",
    "ancestors": [{"id": <PARENT_PAGE_ID>}],
    "space": {"key": "<SPACE_KEY>"},
    "body": {
      "storage": {
        "value": "<ESCAPED_HTML_CONTENT>",
        "representation": "storage"
      }
    }
  }' \
  "${CONFLUENCE_BASE_URL}/rest/api/content"
```

**Important:** The HTML content in `body.storage.value` must be properly JSON-escaped (escape double quotes, backslashes, newlines).

## Important Rules

1. **Never merge anything.** This skill only runs AFTER all MRs are already merged.
2. **Always verify MR status before deleting branches.** If any MR is still open, halt completely.
3. **Use `git branch -D`** (force delete) for local branches since the MR is confirmed merged.
4. **If `-D` fails with "not fully merged"**, STOP — this indicates an anomaly that needs investigation.
5. **JIRA failures do not block the skill.** Branch cleanup is the primary objective. JIRA updates are best-effort.
6. **Present the verification summary** (Step 3.5) and get confirmation before deleting any branches.
7. **Do not delete the `develop` branch** — only delete `develop-{ISSUE_ID}` feature branches.
8. **Preserve artifacts.** Do not delete feature specs, implementation plans, or any files in the working tree. Only git branches are cleaned up.
9. **Never force-push.** Only delete branches and prune.
10. **`ai/` repo commit failure is non-blocking.** If committing to the `ai/` repo fails, report and continue. The primary objectives (branch cleanup, JIRA update) take priority.
11. **Confluence documentation is mandatory.** If Confluence credentials are missing, prompt the user to provide them. If the user explicitly requests to skip, allow it but log a warning. If the Confluence API is unreachable after retries, log the error and continue — the user can re-run `/sdd-wrap-up` to publish later. If a page already exists, update it in place.
12. **Knowledge integration is deferred.** This skill does not update AGENTS.md, knowledge specs, or LEARNINGS.md. Use the `update-knowledge` skill for that.
13. **Spec is the primary issue.** If the user provides a Story, resolve it to a Spec via `/sdd-story-to-spec` (Step 1A). All artifacts, comments, labels, and transitions target the Spec. The linked Story receives condensed dual-updates (Steps 6.4, 7.4) that are **non-blocking** — Story update failures never fail the skill.

## API Reference

### GitLab

|| Action | Method | Endpoint |
||---|---|---|
|| List merged MRs | `GET` | `/projects/:id/merge_requests?source_branch=:branch&target_branch=develop&state=merged` |
|| List open MRs | `GET` | `/projects/:id/merge_requests?source_branch=:branch&target_branch=develop&state=opened` |
