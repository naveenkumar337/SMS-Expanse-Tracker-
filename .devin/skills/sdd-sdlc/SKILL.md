# Skill: sdlc

> End-to-end SDLC orchestrator. Given a single issue ID, drives the complete lifecycle autonomously with only **3 user checkpoints**. Also the entry point when `/sdd-fix` escalates a Tier 4 change.

---

## Orchestrator Principle

**This skill is a pure sequencer.** It calls sub-skills in order and manages user checkpoints between them. It does **not**:

- Fetch JIRA issues (that's `/sdd-create-specs`'s job)
- Generate specs, plans, or contracts (each sub-skill owns its own output)
- Perform JIRA status transitions (each sub-skill handles its own transitions)
- Run RRG, TRC, or any evaluation logic (those live inside `/sdd-create-specs`)

If a user says "skip JIRA", this orchestrator does **not** skip any sub-skill calls. JIRA interaction decisions are made **inside** each sub-skill, not here. The orchestrator's only job is: call the next sub-skill → present checkpoint → wait → call the next.

---

## User Checkpoints

| # | When | What the user does | What happens next |
|---|------|-------------------|-------------------|
| **1** | After feature spec is generated | Review `specs.md`, answer open questions, iterate until requirements are clear | Agent proceeds to create implementation plan |
| **2** | After implementation plan is generated | Review `plan.md`, iterate until the plan is perfect — discuss design decisions, file choices, test strategy | Agent proceeds to implement, push, and create MRs |
| **3** | After MRs are created and human reviewer adds comments | Add review comments on the actual code diffs in GitLab | Agent fixes accepted comments, replies to rejected ones, pushes updates |

Between checkpoints, everything runs autonomously. Each sub-skill handles its own JIRA updates, Git operations, builds, tests, commits, pushes, MR creation, and cleanup.

---

## Prerequisites

- `local.config` at workspace root with `GIT_PAT` (GitLab API). JIRA operations use the `jira-it` MCP server; `JIRA_PAT`/`JIRA_BASE_URL` in `local.config` are fallback only.
- The issue exists in JIRA with summary, description, and acceptance criteria. The issue can be either a **Story** or a **Spec** — the orchestrator handles Story-to-Spec conversion automatically.
- POD knowledge at `ai/knowledge/` (if missing, the orchestrator runs `/sdd-create-pod-knowledge` first).
- `AGENTS.md` at workspace root (generated by `/sdd-create-pod-knowledge`).
- Network access to JIRA and GitLab remotes.

## Step 0 — Story-to-Spec Resolution

**Before any state detection or skill steps**, resolve the input issue to a Spec:

1. Fetch the issue: `jira_get_issue` with `fields: issuetype,summary,issuelinks`
2. Read `issuetype.name`:
   - If **`Spec`** → proceed with this issue as `{ISSUE_ID}`. Scan `issuelinks` for a linked Story → record as `{LINKED_STORY_ID}` (or null).
   - If **`Story`** → invoke `/sdd-story-to-spec {ISSUE_ID}`:
     - If a linked Spec already exists, it is returned directly (no duplicate created)
     - If no linked Spec exists, a new Spec is created, linked, and returned
     - Record the returned Spec ID as the new `{ISSUE_ID}`
     - Record the original Story ID as `{LINKED_STORY_ID}`
   - If **any other type** → check `issuelinks` for a linked Spec. If found, use it. Otherwise, invoke `/sdd-story-to-spec`.

Announce the resolution:

```
=== Issue Resolution ===

Input:          {original issue ID} ({issuetype.name})
Spec (primary): {ISSUE_ID}
Linked Story:   {LINKED_STORY_ID or "None"}

All SDD artifacts will reference Spec {ISSUE_ID}.
{If LINKED_STORY_ID: "Story {LINKED_STORY_ID} will be kept in sync at each milestone."}
```

**All subsequent steps — including State Detection — use `{ISSUE_ID}` (the Spec).** The `{LINKED_STORY_ID}` is passed to each sub-skill, which handles its own Story sync (see the Dual-Update Convention in `/sdd-story-to-spec`).

## State Detection & Mid-Flow Entry

The `/sdd-sdlc` orchestrator is **re-entrant** — it can be invoked at any point in the lifecycle and will intelligently pick up from where the feature left off.

### State Detection Logic

On invocation, run these checks in order:

```
1. Check if ai/specs/{ISSUE_ID}/ exists
   └─ NO  → State: FRESH — start from Step 1

2. Check if specs.md exists
   └─ NO  → State: FRESH — start from Step 1

3. Check if plan.md exists
   └─ NO  → State: SPEC_READY — start from Step 3

4. Check for open MRs (source_branch=develop-{ISSUE_ID}, state=opened)
   └─ YES → Check for unresolved review comments
            ├─ YES → State: MR_REVIEW — start from Step 5
            └─ NO  → State: MR_OPEN — go to Step 6

5. Check for merged MRs (source_branch=develop-{ISSUE_ID}, state=merged)
   └─ YES → Check if wrap-up was completed (Confluence page exists or JIRA status is Complete/Done)
            ├─ YES → State: COMPLETE — report already done
            └─ NO  → State: MR_MERGED — start from Step 7

6. Check for feature branches (develop-{ISSUE_ID} exists locally)
   └─ YES → State: IMPL_READY — start from Step 4
   └─ NO  → State: PLAN_READY — start from Step 4
```

### Entry Point Summary

| Detected State | Artifacts Present | Entry Point | What Happens |
|---|---|---|---|
| **FRESH** | Nothing (or no specs.md) | Step 1 | Full flow from the beginning |
| **SPEC_READY** | `specs.md` exists, no plan | Step 3 | Create plan → Checkpoint 2 → execute |
| **PLAN_READY** | Spec + plan exist, no MRs, no branches | Step 4 | Execute (creates branches, implements, pushes, creates MRs) |
| **IMPL_READY** | Spec + plan + feature branches, no MRs | Step 4 | Resume execute (detects existing branches) |
| **MR_REVIEW** | Open MRs with unresolved comments | Step 5 | Fix MR comments via `/sdd-execute` re-entry |
| **MR_OPEN** | Open MRs, no unresolved comments | Step 6 | Waiting for merge |
| **MR_MERGED** | Merged MRs, wrap-up not done | Step 7 | Run wrap-up |
| **COMPLETE** | Merged MRs + wrap-up done | — | Report: feature already complete |

### State Announcement

On detecting the current state, announce clearly:

```
=== SDLC State Detection for {ISSUE_ID} ===

Current state: {STATE_NAME}
  - specs.md:              {EXISTS / MISSING}
  - plan.md:               {EXISTS / MISSING}
  - Feature branches:      {EXIST in N projects / NONE}
  - Open MRs:              {N open / NONE}
  - Unresolved comments:   {N comments / NONE}
  - Merged MRs:            {N merged / NONE}
  - Wrap-up completed:     {YES / NO}

→ Entering at: Step {N} — {step description}
```

If not FRESH, ask user to confirm before proceeding.

## Orchestration Flow

```
Input: Issue ID (e.g. PROJECT-1234) — can be a Story or a Spec

Phase 0: RESOLUTION (autonomous)
  |
  +--> Step 0: Story-to-Spec resolution
  |      (if Story: create/find linked Spec via /sdd-story-to-spec)
  |      Result: {ISSUE_ID} = Spec, {LINKED_STORY_ID} = Story (or null)
  |
Phase 1: ANALYSIS (autonomous)
  |
  +--> Step 1: Verify POD knowledge
  +--> Step 2: /sdd-create-specs {ISSUE_ID}
  |      (internally: JIRA fetch, RRG, TRC, spec gen, contract gen)
  |
  === CHECKPOINT 1: User reviews feature spec ===
  |
Phase 2: PLANNING (autonomous)
  |
  +--> Step 3: /sdd-create-plan {ISSUE_ID}
  |      (internally: spec + contract verification, architectural assessment, plan gen)
  |
  === CHECKPOINT 2: User reviews implementation plan ===
  |
  +--> HARD GATE: verify specs.md + plan.md exist before proceeding
  |
Phase 3: EXECUTION (autonomous)
  |
  +--> Step 4: /sdd-execute {ISSUE_ID}
  |      (internally: artifact verification, branch, TDD, commit, push, MRs)
  |
  === CHECKPOINT 3: Human reviewer adds MR comments ===
  |
Phase 4: REVIEW & CLOSE (autonomous)
  |
  +--> Step 5: Fix MR review comments (/sdd-execute re-entry)
  +--> Step 6: Wait for MR merge
  +--> Step 7: Close & clean up (/sdd-wrap-up)
  |
  Done.
```

## JIRA Transition States

Each sub-skill transitions the JIRA issue through the following states. Both the Spec (primary) and the linked Story (if present) are transitioned at each stage.

| SDD Phase | Sub-Skill | Action Trigger | Target Jira State | Description |
|-----------|-----------|----------------|-------------------|-------------|
| Specs | `/sdd-create-specs` | Create Specs | **DEFINING DETAILS** | Move issue from PROPOSED into active specification work |
| Plan | `/sdd-create-plan` | Create Plan | **READY FOR DEV** | Specs are complete; issue is ready for a developer |
| Execute | `/sdd-execute` | Execute Start | **IN DEVELOPMENT** | Developer has started active coding / implementation |
| After Completion | `/sdd-execute` | Completion Confirmed | **READY TO DEPLOY** | Dev work done; issue is staged and ready for deployment |
| Wrap Up | `/sdd-wrap-up` | Wrap Up | **COMPLETE** | Deployment done and issue fully closed out |

> **Note:** Each sub-skill handles its own JIRA transitions internally (including dual-update to the linked Story). The orchestrator does not perform any transitions directly.

## Skill Steps

### Step 1 — Verify POD Knowledge

Check if `ai/knowledge/` contains the core spec files (`functional-spec.md`, `technical-spec.md`, `data-model-spec.md`, `api-spec.md`) and `AGENTS.md` exists at workspace root.

**AGENTS.md validation:** `AGENTS.md` must exist AND be populated with real content — not just template headings. Verify it contains at minimum: project name, tech stack, build commands, test commands, and module-to-project mapping. If `AGENTS.md` exists but contains only empty template sections (headings with no content, placeholder text like `TODO`/`TBD`), treat it as missing.

If any core spec file is missing OR `AGENTS.md` is missing/empty, run `/sdd-create-pod-knowledge` first. This is a one-time setup cost.

---

### Step 2 — Generate Feature Spec

Run `/sdd-create-specs {ISSUE_ID}`.

The sub-skill handles everything autonomously: JIRA fetch, RRG evaluation (Step 2A), TRC evaluation (Step 2B), POD knowledge loading, codebase analysis, spec generation, integration contract generation, and JIRA status transition to **Defining Details**.

> **Do not duplicate any of this logic here.** If the user wants to skip JIRA, that decision is made inside `/sdd-create-specs`, not in this orchestrator.

After generation, present the `create-specs` summary output (Step 7 of `/sdd-create-specs`) as Checkpoint 1:

```
=== CHECKPOINT 1: Feature Spec Review ===

{create-specs Step 7 summary: Issue, Output path, Contract, RRS, TRC, FRs, Impacted areas, Interlocks, Open Questions, Auto-Resolved Assumptions}

Please review the feature spec and:
1. Answer the open questions above
2. Review auto-resolved assumptions — override any that are incorrect
3. Confirm the requirements are correct and complete
4. Review the interlock map and per-interlock contracts for accuracy
5. Flag anything that needs changes

Reply when ready to proceed to implementation planning.
```

**WAIT for user response.** Iterate on the spec based on feedback until the user confirms it's ready.

---

### Step 3 — Generate Implementation Plan

Run `/sdd-create-plan {ISSUE_ID}`.

The sub-skill handles everything autonomously: spec + contract verification, RRS threshold check, architectural assessment, codebase analysis, local simulation planning, plan generation, and JIRA status transition to **Ready for Dev**.

> **Do not duplicate any of this logic here.**

After generation, present the `create-plan` summary output (Step 6 of `/sdd-create-plan`) as Checkpoint 2:

```
=== CHECKPOINT 2: Implementation Plan Review ===

{create-plan Step 6 summary: Feature, Plan path, Projects, Files to modify, Test cases, Local sim, Architecture, Open Questions}

Please review the implementation plan and:
1. Resolve any open questions
2. Confirm the file changes are correct
3. Confirm the test strategy
4. Flag any design decisions you want to change

Reply when ready to proceed to implementation.
```

**WAIT for user response.** Iterate until the user confirms the plan is ready.

---

### Hard Gate — Pre-Execution Verification

Before proceeding to Step 4, verify **both** artifacts exist:

```
1. ai/specs/{ISSUE_ID}/specs.md    → MUST exist
2. ai/specs/{ISSUE_ID}/plan.md     → MUST exist
```

**If either is missing, STOP.** Do not proceed to execution under any circumstances. Direct the user to the missing sub-skill:
- No spec → "Run `/sdd-create-specs {ISSUE_ID}` first"
- No plan → "Run `/sdd-create-plan {ISSUE_ID}` first"

This gate exists because no user instruction (e.g., "skip JIRA", "just implement", "go fast") should bypass spec and plan generation. The orchestrator never generates code without a spec and plan.

---

### Step 4 — Execute Implementation + Push + MRs (autonomous)

Run `/sdd-execute {ISSUE_ID}`.

The sub-skill handles everything autonomously: artifact verification, branch creation, TDD implementation, cross-project verification, local testing checkpoint, commit, push, submodule reference updates, MR creation, change-summary generation, and JIRA status transitions (**In Development** at start, **Ready to Deploy** at completion).

> **Do not duplicate any of this logic here.**

After MRs are created, present Checkpoint 3:

```
=== MRs Created — Ready for Review ===

| # | Project | MR | URL |
|---|---------|-----|-----|
| 1 | {project-name} | !{iid} | {url} |
| N | ai | !{iid} | {url} |

Please review the code diffs in GitLab and add your review comments.

=== CHECKPOINT 3: Waiting for MR Review Comments ===

When you've finished adding review comments to the MR(s), reply here
and I'll address them — implementing accepted suggestions and replying
to any I disagree with.
```

**WAIT for user response.** The user opens MR URLs in GitLab, reviews diffs, adds comments, then returns.

---

### Step 5 — Fix MR Review Comments (autonomous)

Re-run `/sdd-execute {ISSUE_ID}`. It automatically detects existing MRs with unresolved comments and enters the **MR Review Fix Phase** — fetching discussions, analysing each comment, making targeted code changes, pushing, and replying on GitLab.

If the reviewer adds more comments after this round, the user can trigger this step again.

---

### Step 6 — Wait for MR Merge (user-driven)

After MR comments are addressed, the MR needs human approval and merge in GitLab.

```
=== Waiting for MR Merge ===

All review comments have been addressed. Next steps:
1. Reviewer approves the MR(s) in GitLab
2. Reviewer (or you) merges the MR(s) to develop
3. Once merged, reply here and I'll clean up

MR URLs:
{list MR URLs from change-summary.md}
```

**WAIT for user to confirm MRs are merged.**

---

### Step 7 — Wrap Up (autonomous)

Run `/sdd-wrap-up {ISSUE_ID}`.

The sub-skill handles everything autonomously: MR merge verification, branch cleanup (local + remote), switch to `develop` + pull latest, JIRA coding summary comment, `AI-Delivered` label, transition to **Complete**, Confluence documentation, and ai/ repo sync.

> **Note:** Knowledge base updates (`AGENTS.md`, `LEARNINGS.md`, `ai/knowledge/`) are handled by `/sdd-update-knowledge`, run periodically by the POD lead on `develop`.

Report:

```
=== SDLC Complete for {ISSUE_ID} ===

Feature:       {summary}
Linked Story:  {LINKED_STORY_ID or "None — Spec provided directly"}
Status:        Complete

Branch cleanup:   All feature branches deleted
JIRA:             Spec transitioned to Complete
Story sync:       {LINKED_STORY_ID} transitioned to Complete (or "N/A")
MRs:              All merged to develop
Confluence:       Published (or: skipped/failed)

Artifacts retained:
- ai/specs/{ISSUE_ID}/specs.md
- ai/specs/{ISSUE_ID}/plan.md
- ai/specs/{ISSUE_ID}/change-summary.md

Next: Run /sdd-update-knowledge periodically to batch-integrate into ai/knowledge/
```
