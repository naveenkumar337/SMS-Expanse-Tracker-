# Skill: create-plan

> Generate a detailed `plan.md` from an existing feature spec. The plan covers what to change, how to change it, architectural decisions, and how to simulate the full flow locally.

---

## Pre-Execution Directive — Always-On Rules

**Mandatory.** Before starting this skill, read `.devin/rules/architecture-standards.md`.
RULE 0 in that file defines how every rule applies at each step of this skill.
RULE 1 defines MCP availability handling — if the `standards-fabric` MCP server
is configured but unreachable, the skill continues (not blocked); see RULE 1 for details.

---

## Prerequisites

- A feature spec must exist at `ai/specs/{ISSUE_ID}/specs.md` (generated by `/sdd-create-specs`).
- `AGENTS.md` at workspace root for project structure, tech stack, and build commands.
- POD knowledge under `ai/knowledge/` for architecture and domain context.

## Step 1 — Verify Spec & Resolve Open Items

Accept the JIRA Issue ID. This should be a **Spec** issue ID (resolved by `/sdd-create-specs` or `/sdd-sdlc`).

### Step 1.0 — Resolve Linked Story

Check if the Spec has a linked Story for dual-update purposes:

1. Fetch the issue: `jira_get_issue` with `fields: issuetype,issuelinks`
2. If `issuetype.name` is `Story` (user provided a Story ID directly):
   - Scan `issuelinks` for a linked Spec. If found, switch to the Spec ID.
   - If no linked Spec exists, invoke `/sdd-story-to-spec {ISSUE_ID}` and use the returned Spec ID.
3. If `issuetype.name` is `Spec`:
   - Scan `issuelinks` for a linked Story. Record as `{LINKED_STORY_ID}` (or null if none).
4. Record `{LINKED_STORY_ID}` for dual-update in Step 5A.

Verify `ai/specs/{ISSUE_ID}/specs.md` exists — if not, stop and direct the user to run `/sdd-create-specs` first.

**Requirement Readiness check:** Read Section 4.0 (Requirement Readiness Assessment) of the spec. Read the `Threshold Applied` field — this is the calibrated Green threshold from RRG §3E based on Phase 1A Criticality Tier and Lifecycle Stage. If no `Threshold Applied` field exists (pre-v1.2.0 spec), fall back to ≥ 80%. If Section 4.0 is absent or RRS is below the applicable threshold, stop and direct the user to re-run `/sdd-create-specs` to complete the Requirement Readiness Gate before planning.

**Phase 1A Classification check:** Verify Section 4.0 contains the Software Classification sub-table with all 13 Phase 1A dimensions populated and evidence-cited. If missing or incomplete, stop — the spec must be re-evaluated via `/sdd-create-specs`.

**Integration Contract check:** Check if `ai/contracts/{ISSUE_ID}/contract.md` exists. If present, load it — the interlock map and per-interlock contracts are primary inputs to architectural decisions in Step 2. If absent, verify this is intentional (spec has zero interlocks, e.g., pure refactor). If the spec references interlocks but no contract exists, stop and direct the user to re-run `/sdd-create-specs`.

**Input Fidelity check:** Verify Section 4.0B (Input Fidelity) exists in the spec. If present, confirm all 🔶 Fidelity items show status ✅ Resolved. If any 🔶 item is unresolved, stop — the spec has unverified placeholder content that will pollute the plan. Direct the user to re-run `/sdd-create-specs`. If Section 4.0B is absent (spec predates fidelity scanning), run a lightweight fidelity check (RRG §Phase 1B signals S1 and S2 only) on the spec's §4.5 (FRs) and §4.6 (ACs). Flag and resolve issues before proceeding.

**Delivery context:** Read `JIRA Integration`, `Concurrency & Throughput Profile`, and `Delivery Scope` from spec Section 4.0. Carry all three forward — do not re-decide them. If `JIRA Integration = Disabled (local mode)`, every JIRA operation in this skill (Step 5) is skipped. If the field is absent (pre-existing spec), treat JIRA as Enabled only when a real JIRA ID is present and reachable.

**Delivery Scope Binding:** Read `Delivery Scope` from spec Section 4.0. If absent (pre-v1.3.0 spec), derive it: read Phase 1A Lifecycle Stage (A3) from the Software Classification sub-table — `Production`, `MVP`, `Legacy`, or `Deprecated` → `Full Production`; `Prototype` with user-confirmed PoC intent → `Proof of Concept`; otherwise default to `Full Production`. Record the resolved value in the plan header (Section 1). This binding is a **contract** — `/sdd-execute` reads it and must implement every Section 5 item to completion when `Full Production`. Every item in Section 5 (Implementation Order) is **mandatory** under `Full Production` scope — do not mark any item as optional, deferred, or "nice to have". If a component requires external infrastructure that cannot be accessed during implementation, implement the production client code with externalized configuration — do not substitute it with a stub or simulation.

Scan the **entire spec body** — §4.2 through §4.9 — for unresolved items: open questions (not marked `[RESOLVED]`), `[AUTO-RESOLVED]` assumptions, and any `TBD`/`TODO`/`N/A` (as placeholder value)/`To be confirmed`/`TBC` markers.

**Under Full Production scope:** `TBD`/`TODO` markers found in §4.5 (Functional Requirements), §4.6 (Acceptance Criteria), §4.7 (Non-Functional Requirements), or §4.8 (Impacted Areas) are **hard blockers** — these sections must contain concrete, production-grade content. Present them to the user and **wait** for real values before proceeding. Do not auto-resolve TBD items with assumptions.

`TBD` in §4.9 (Open Questions) is acceptable **only** if the items are explicitly marked as `[TBD — USER-ACKNOWLEDGED: {justification}]` — meaning the user consciously deferred them during spec creation with a stated reason.

**If any hard blockers exist:** present them all in a single prompt and **wait** for answers. Update the spec with responses. Do not proceed with unresolved ambiguities in production-critical sections.

**If all resolved (or only USER-ACKNOWLEDGED items in §4.9):** proceed.

## Step 2 — Architectural & Infrastructure Assessment

Before diving into code, assess the **architectural implications** of the feature. Not every feature needs all of these — evaluate judiciously and ask the user when a decision has business or cost impact.

> **Cross-reference existing spec artifacts before assessing:** Consult §4.0 (RRG — use confirmed dimension answers as inputs; only probe partial fills or new planning-stage details), §4.0A (TRC — don't re-evaluate resolved tactical checks; they directly inform concerns like Database, Deployment, Execution nature), and `ai/contracts/{ISSUE_ID}/contract.md` (interlock schemas, auth, SLA — refine TBD items and update contract). These are primary inputs; do not re-ask what has already been captured.

### 2A — Assess & Decide (only what applies)

| Concern | When to Assess | What to Decide |
|---|---|---|
| **Technology stack** | Feature introduces a new technology or library not in `AGENTS.md` | Justify the addition. Check compatibility with existing stack. Flag for user approval. |
| **Execution nature** | Feature involves I/O, messaging, or long-running operations | Sync vs async. Blocking vs non-blocking. Reactive vs imperative. Must align with existing codebase patterns. |
| **Application layers** | Feature touches multiple layers | Which layers are impacted: presentation, service/business, data/repository, integration. Map the data flow through each layer. |
| **Data flow & transformation** | Feature moves data between systems or reshapes data | Document: source → transformations → destination. Note data types, formats, serialization (JSON, Avro, Protobuf). |
| **Upstream/downstream messaging** | Feature publishes or consumes messages | Topic/queue names, message schema, serialization format, delivery guarantees (at-least-once, exactly-once). How to handle poison messages. |
| **Database & persistence** | Feature reads/writes data | New collections/tables, indexes, migrations. Transactional vs non-transactional data — impacts SLA decisions. |
| **Authentication & authorization** | Feature exposes endpoints or accesses protected resources | Auth mechanism (JWT, OAuth, API key). RBAC/ABAC. Access control at which layer. Align with existing auth patterns. |
| **Scalability & load balancing** | Feature handles high throughput or concurrent access | Horizontal scaling strategy. Stateless vs stateful. Partitioning. Connection pooling. Rate limiting. **In-process concurrency:** when §4.0 Concurrency & Throughput Profile states high throughput/concurrency numbers, also decide the threading/async model and thread/connection-pool sizing needed to meet them — not only horizontal scaling — and capture as Section 5 tasks. |
| **SLA & resilience** | Feature has availability or latency requirements | Define SLA based on data nature: transactional data (strict consistency, higher SLA) vs non-transactional (eventual consistency, relaxed SLA). Circuit breakers, retries, fallbacks. |
| **Deployment** | Feature requires new infrastructure or deployment changes | Target platform (K8s, PCF, VM). New services, sidecars, config maps, secrets. CI/CD pipeline changes. **Deployment artifact check:** RRG Phase 1A classifies the Deployment Model (Containerized, PaaS, Serverless, VM, Library). If TRC check 7.6 flagged the deployment artifact as missing, include creation of the appropriate artifact (Dockerfile for Containerized, manifest.yml for PaaS, serverless.yml for Serverless, Helm chart for K8s-managed, etc.) as an explicit implementation task in Section 5. Reference existing deployment artifacts in the workspace for conventions. |

#### 2A.1 — Phase 1A-Driven Assessment

Before evaluating the concern table above, read the Phase 1A Software Classification from spec Section 4.0. These classifications modify how concerns are assessed:

| Phase 1A Dimension | Impact on Planning |
|---|---|
| **Criticality = Mission-critical** | Test strategy must include: stress testing, failure injection, rollback dry-run. Local simulation setup is mandatory (not optional). |
| **Criticality = Best-effort** | Lighter test strategy acceptable. Local simulation optional if unit tests provide adequate coverage. |
| **Lifecycle = Prototype/MVP** | Skip heavy infrastructure planning (no HA, no multi-region). Deployment artifact is sufficient as a basic Dockerfile or equivalent. Skip performance tuning. |
| **Lifecycle = Legacy/Deprecated** | Emphasize backward compatibility. No architectural changes unless explicitly required. Regression test suite is primary quality gate. |
| **Statefulness = Stateful** | Plan must address: session replication/stickiness for scaling, state migration for rollback, state backup for disaster recovery. Add to Section 5 implementation tasks if not already handled. |
| **Runtime Model = Batch/Scheduled** | Plan must include: job scheduling configuration, DST-safe cron expressions, job completion monitoring, retry strategy for failed batches, data checkpoint/resume mechanism for large batches. |
| **Runtime Model = Streaming** | Plan must include: consumer group configuration, offset management, backpressure handling, exactly-once vs at-least-once processing decision, event replay capability. |
| **Data Volume = Large/Massive** | Plan must include: chunked migration strategy (not single-transaction), index rebuild time estimates, test data sampling strategy (full volume not practical in local), pagination for all queries. |
| **AI/ML Component ≠ None** | Plan must include: model hosting strategy (self-hosted vs API), GPU/accelerator requirements for local dev, model versioning approach, inference latency budget, eval metrics and acceptance thresholds. If training: data pipeline, training infrastructure, experiment tracking. |
| **Multi-tenancy = Multi-tenant** | Plan must verify: tenant isolation in every data query, tenant-scoped caching, tenant ID propagation through all service layers, cross-tenant data leakage test cases. |
| **Data Sensitivity = Confidential/Restricted** | Plan must include: encryption at rest and in transit, PII masking in logs and test data, data access audit logging, compliance-specific test cases (GDPR right-to-deletion, etc.). |
| **RRG D6/D7 = high throughput / high concurrency** (see §4.0 Concurrency & Throughput Profile) | Do not stop at horizontal scaling. Plan the **in-process concurrency model** explicitly and add it as concrete Section 5 tasks: threading / async model (worker pool, reactive, event loop) aligned to existing patterns; **thread-pool and connection-pool sizing derived from the target throughput/concurrency numbers**; batching / bulkheads / backpressure for overload; idempotency where parallel processing can duplicate work. Record the sizing rationale (e.g. "pool = 32 to sustain 5k msg/s at ~6ms/msg") in Section 2 Architectural Decisions. |

### 2B — Brownfield Rule

If this is a brownfield change (modifying an existing system), **silently align** with the current architecture and design patterns. Do not propose architectural changes unless the spec explicitly demands them. Read existing code to discover patterns — don't impose new ones.

### 2C — Local Simulation Environment

If the feature depends on external infrastructure (message brokers, databases, downstream services, etc.), the plan **must include** a local simulation setup so developers can test the full flow on their machine.

Identify every external dependency the feature touches and plan a local substitute for each — this could be containerized services, in-memory alternatives, embedded servers, mock/stub services, or any approach that fits the project's existing local dev setup.

#### 2C.1 — Workspace Topology Assessment

Before planning local substitutes, classify every component involved in the feature using the Software Classification from RRG Phase 1A (Workspace Scope dimension):

```
=== Workspace Topology ===

| Component | Role | In Workspace? | Path / URL | Local Substitute |
|---|---|---|---|---|
| {app-name} | Central app | YES | ai/submodules/{project} | Runs directly |
| {db-name} | Interlock (DB) | NO | {host:port from contract} | Testcontainers / embedded DB |
| {api-service} | Interlock (API) | YES | ai/submodules/{other} | Runs locally |
| {vault} | Interlock (Auth) | NO | {url from contract} | Mock / dev container |
| {queue} | Interlock (MQ) | NO | {broker URL from contract} | Embedded broker / Testcontainers |
```

This classification drives test strategy decisions in Section 5:
- **Both components Local:** Integration tests can use real local instances — no mocks needed.
- **Central app Local, interlock Remote:** Integration tests must use stubs/mocks for the remote interlock. Plan the mock in Section 6.
- **Interlock Remote with no local substitute possible:** Flag in Section 5 as `[REQUIRES_REMOTE_ACCESS]` and document the exact access needed.

> **Source:** Workspace Scope is captured in RRG Phase 1A. If not available (e.g., abbreviated RRG in Tier 3), scan the workspace (`ai/submodules/`, workspace root) to classify each component.

#### 2C.2 — Data & AI Considerations for Local Simulation

If Phase 1A classifications indicate data or AI concerns, the local simulation must account for them:

| Phase 1A Value | Local Simulation Requirement |
|---|---|
| **Data Volume = Large/Massive** | Do NOT use full production data volume for local testing. Plan a representative sample dataset (seed data) that covers edge cases within a manageable size (<1 GB for local). Document the sampling strategy in Section 6. |
| **AI/ML Component ≠ None** | If model inference is required locally: provide a pre-trained model artifact (not training from scratch). If GPU is needed but unavailable locally: provide a CPU-compatible model variant or mock the inference endpoint. Document model artifact location and version in Section 6. |
| **Data Sensitivity = Confidential/Restricted** | Local test data must be anonymized/synthetic — never use production PII for local testing. Document the anonymization strategy in Section 6. If no synthetic data generator exists, create one as an implementation task in Section 5. |
| **Statefulness = Stateful** | Local simulation must include the state store (Redis, session store, etc.) in the infrastructure setup. Seed data must include session/state fixtures for integration testing. |

The plan should specify:
- **Local substitutes** for every external dependency (what technology, how to run it)
- **Seed data / fixtures** for databases or data stores
- **Test payloads** for message brokers or event streams
- **Stub services** for downstream dependencies (returning canned responses)
- **Observability tooling** for local debugging — only if not already set up
- **Application in local setup** — include the application itself, not just infrastructure dependencies. When the app runs in a networked environment, its connection config must use the correct internal service addresses for the chosen run mode.
- **Credential & connection mapping** — for every service the app connects to, the plan MUST document both sides: (a) what the service initialisation creates (user, password, auth scope, port) and (b) what the app's connection config expects. Use the **Credential & Connection Mapping** table in Section 6. This is the #1 source of silent failures.
- **Auth protocol override** — if the app defaults to a secured protocol in production, explicitly override to dev/no-auth mode in the local config.
- **Security test contingency** — if the RRG Phase 1A Security Testability is `Restricted` (auth mechanism cannot be replicated locally — e.g., SSO with corporate IdP, vault with production-only policies, mTLS with org-issued certs):
  1. **Preferred:** Configure a dev/no-auth override mode for local testing (document the override config).
  2. **Fallback:** If no dev mode exists, plan mock/stub auth responses (e.g., WireMock returning valid tokens, test vault with dev policies, mock IdP).
  3. **Last resort:** If neither is possible, document the gap clearly: "Auth for {component} cannot be tested locally. Requires {specific access/config}." Ask user to provide: dev credentials, test IdP config, or vault dev policy.
  4. Include this contingency in the test strategy (Section 5) — affected integration tests should be marked with `[REQUIRES_AUTH_SETUP]` and include setup instructions.
- **Run mode clarity** — state which mode(s) the setup supports:
  - Mode A: App on developer's host; dependencies managed separately (host-reachable addresses)
  - Mode B: All components managed together (internal service addresses)
- **Test artifacts under `tests/`** — stubs, mocks, seed scripts, and fixtures live under `tests/`, not at the project root.

> **Enforcement:** these rules are verified during implementation by `/sdd-execute` Step 8B (Artifact Cross-Validation). Section 6 documents the expected values; Step 8B reads actual generated files and cross-compares.

> **Example approaches:** a service with messaging + DB dependencies might use containerised local services (Docker Compose, Podman, Testcontainers), embedded in-process alternatives (H2, embedded Kafka, in-memory brokers), or WireMock/Hoverfly/MSW stubs for downstream APIs — use whatever fits the project's existing local dev setup.

If the project already has a local dev setup, **extend it** rather than creating a new one. Check for existing orchestration files, `Makefile` targets, dev scripts, or `README.md` instructions.

**If not needed** (e.g., simple CRUD with existing local setup): skip this section silently.

### 2D — Missing Data: Configuration Placeholders

If the feature depends on values not yet defined in the spec — field mappings, environment-specific endpoints, integration credentials, routing rules, or any configuration that is feature-specific and may vary by environment:

**Clarify before you defer.** Collect *all* such missing values into a **single consolidated question** and ask the user once — do not silently jump to TBD. Present them together:

```
=== Missing Configuration — please provide or defer ===
The plan needs the following values. Provide any you know now; reply "defer" for any that must be resolved later.

1. {config item} — {what it controls} — {component that uses it}
2. {config item} — ...
```

- For every value the user supplies, record it in the plan and mark `[RESOLVED]`.
- Only values the user cannot provide (or explicitly defers) become TBD. **Do NOT hardcode placeholder values in production code.** For each deferred value:
  1. Add a row to **Section 10 — Configuration Placeholders** (see template below), status `TODO`
  2. Implement using externalized config (environment variables, config maps, feature flags) — never inline
  3. At each usage site in code, add: `# TODO: resolve before production — see plan.md Section 10`

Every deferred value MUST also appear in the **⚠️ Deferred / TBD Items** highlight of the Step 6 output so it is impossible to miss. If no missing data is identified, skip this step silently.

### 2E — Greenfield / New Project Detection

Determine whether the feature can be delivered entirely within **existing** projects (brownfield) or whether it requires one or more **brand-new projects** to be created (greenfield). This distinction drives the bootstrap logic in `/sdd-execute` Step 4B.

**A project is greenfield (new) when ANY of the following is true:**
- The spec calls for a new service/component/library that has no corresponding directory in the workspace.
- There is no matching entry in the workspace-root `.gitmodules` for the target project.
- `AGENTS.md` does not map any module to the target project.
- No GitLab remote exists yet for the target project (it has never been created).

**For every impacted target, classify it:**

| Target | Classification | Evidence |
|---|---|---|
| `{project-dir}` | Brownfield (exists) | Directory + `.gitmodules` entry + AGENTS.md mapping present |
| `{new-project-dir}` | Greenfield (new) | No directory / no `.gitmodules` entry / no remote |

**For each greenfield project, capture the following** — these become the **Section 3A — New Projects to Create** entries in the plan and are consumed by `/sdd-execute` Step 4B (Project Bootstrap):

- **Project directory name** (workspace-relative, e.g. `payment-gateway`) and submodule path (e.g. `ai/submodules/payment-gateway`)
- **GitLab namespace / group path** where the new repo must be created (ask the user if the spec does not state it — do not guess)
- **Repository name** and description
- **Technology stack** — language, framework, runtime version (from spec technology constraints and §2A). This determines the scaffold: `pom.xml` (Java/Maven), `build.gradle` (Gradle), `package.json` (Node), `pyproject.toml`/`requirements.txt` (Python), `go.mod` (Go), `Cargo.toml` (Rust), etc.
- **Initial directory layout** — standard source/test layout for the chosen stack.
- **Base branch** — `develop` (the bootstrap will create it from the initial commit).
- **Deployment artifact** — whether a Dockerfile/manifest is required (per Section 5 item 5).

> **User approval:** creating a new GitLab repository is an irreversible, side-effecting action. The plan records the intent; `/sdd-execute` Step 4B presents the full list of projects-to-create and requires explicit user confirmation before calling the GitLab API.

If no greenfield projects are needed, note "No new projects — all changes land in existing projects" and skip Section 3A.

## Step 3 — Codebase Analysis

> **Greenfield note:** For targets classified as greenfield in Step 2E there is no existing code to trace. Skip the call-chain tracing below for those targets and instead design the initial module structure, entry points, and data structures from the spec. Record these as **Section 3A — New Projects to Create** entries (files to create, not modify). Apply the steps below only to brownfield targets that already have code.

Cross-reference the feature spec against the actual codebase. For every impacted area identified in the spec (§4.8), perform the following:

1. **Trace the call chain** — From the entry point (controller/handler) through service → repository → external integrations. Note every class and method in the path.
2. **Identify exact change sites** — File, method, and line range where code will be added, modified, or deleted.
3. **Catalogue data structures** — DTOs, entities, enums, config classes that need new fields, type changes, or new variants.
4. **Map cross-cutting concerns** — Security filters, validation interceptors, logging/observability instrumentation, error-handling middleware that the feature will pass through or modify.
5. **Assess test surface** — Existing test classes, test utilities, mock factories, and fixtures that cover the impacted code. Note gaps (untested paths the plan must address).
6. **Check integration boundaries** — If `ai/contracts/{ISSUE_ID}/contract.md` exists, verify each interlock's code-side implementation (client classes, connection config, retry/circuit-breaker setup) against the contract.

Record every reference as `file path : class/method : line range`. These become the **Section 7 — Files to Modify / Create** entries in the plan.

If `ai/harness/CONSTITUTION.md` exists, verify the planned approach doesn't violate core principles. Block on violations, warn on misalignments.

### Step 3B — Retrospective Spec Updates

During codebase analysis, planning often surfaces information not captured in the original spec. **Update `ai/specs/{ISSUE_ID}/specs.md` immediately** — do not leave these findings only in the plan:

- Missing field definitions or data types discovered in existing code
- Edge cases not covered by acceptance criteria
- API contract gaps (undocumented error responses, missing request/response fields)
- Undocumented business rules found in existing logic
- Config or environment-specific values left undefined in the spec (also add to plan.md Section 10 per Step 2D)

**For each gap found:**
1. Update the relevant section of `specs.md` (FR, AC, NFR, Impacted Areas, or Open Questions)
2. Mark each addition with `[UPDATED-IN-PLANNING]` for traceability
3. Note what was updated in the plan under a "Spec Amendments" note in Section 1

> **Why:** specs are the source of truth. Information discovered during planning that lives only in the plan becomes invisible to `/sdd-wrap-up` documentation, Confluence pages, and future developers reading the spec.

## Step 4 — Generate the Plan

Create the file at `ai/specs/{ISSUE_ID}/plan.md`. The plan must be **self-contained** — an AI agent or developer reading only this file + the feature spec should be able to implement the feature without asking questions.

The plan **must** contain these sections (skip sections marked optional if not applicable):

### Section 1 — Header & Context

```
# Implementation Plan — {ISSUE_ID}: {Feature Title}
```

1–3 paragraphs: what the feature does, which endpoints/services are involved, key technical challenge, reference to example data in `ai/knowledge/data/` if relevant.

### Section 2 — Architectural Decisions *(optional — only if Step 2A produced decisions)*

Document each architectural decision as a concise record:

```markdown
## Architectural Decisions

| # | Decision | Rationale |
|---|---|---|
| AD-1 | Use async processing via Kafka for {X} | High volume; aligns with existing event-driven pattern |
| AD-2 | Add Redis cache for {Y} lookup | SLA requires <50ms; DB query is ~200ms |
```

Include data flow diagram (Mermaid) if the feature involves multi-system data movement.

### Section 3 — Files to Modify

Numbered list. Each entry must include:
- **Full relative path** from project root
- **Exact method names** to add or modify (with approximate line numbers, `~` prefix)
- **What to change** in concrete terms
- **Connections** to other files being changed

### Section 3A — New Projects to Create *(optional — only if Step 2E identified greenfield projects)*

For each brand-new project the feature requires. This section is the authoritative input to `/sdd-execute` Step 4B (Project Bootstrap). Omit entirely if there are no new projects.

```markdown
## New Projects to Create

| # | Project Dir | Submodule Path | GitLab Namespace | Tech Stack | Deploy Artifact |
|---|---|---|---|---|---|
| NP-1 | {project-dir} | ai/submodules/{project-dir} | {group/subgroup} | {lang/framework/runtime} | {Dockerfile / manifest / N/A} |

### NP-1 — {project-dir}
- **Repository name:** {repo-name}
- **Description:** {one line}
- **Base branch:** develop
- **Scaffold files:**
  - {build file, e.g. pom.xml / package.json / go.mod} — {key coordinates: groupId/artifactId, name/version, module path}
  - {README.md, .gitignore, CI config if required by Section 5}
- **Initial directory layout:**
  ```
  {project-dir}/
    src/...            # source layout for the chosen stack
    tests/...          # test layout
    {build-file}
    README.md
    .gitignore
  ```
- **Files to create (initial implementation):** list the first-cut source/test files (these are creates, not modifies).
```

### Section 4 — Files NOT to Modify

Explicit list with reasoning. Prevents scope creep.

```markdown
- No DTO changes — `{field}` already exists on `{DtoClass}`
- No router changes — reuses existing `{METHOD} {PATH}`
```

### Section 5 — Implementation Order

TDD is mandatory. **Unit tests and integration tests serve different purposes and are both required when external dependencies exist.** Unit coverage targets (e.g., ≥80%) do not substitute for integration tests. If Step 2C identified external dependencies, the plan MUST include integration test tasks below.

1. Write unit tests first (list exact test method names and what each tests)
2. Implement to make tests pass
3. Run existing tests — confirm no regressions
4. **Write integration / E2E test scripts** — list the test file path(s) and what flows they cover. These are verified by `/sdd-execute` Step 8 artifact gate.
5. **Deployment artifact** — if the project produces a deployable service (not a library), specify the build/deploy definition to create or update (e.g., Dockerfile, Containerfile, buildpack config, deployment manifest). Include the target runtime version from the spec. Mark `N/A` for libraries.
6. Run full suite
7. **Contract validation tests** — if `ai/contracts/{ISSUE_ID}/` files exist or are generated by this feature, write dedicated contract validation tests:
   - Schema compliance: all required fields present, correct data types
   - Business rule constraints encoded in the contract
   - Boundary conditions: null/optional field handling, edge values
   - Backward compatibility: no existing fields removed or renamed without deprecation
   These must run as part of the standard unit test suite, not as separate integration tests.
8. **Integration test health-check rule** — every integration test that exercises a live flow (not unit-level) must:
   - Verify the **application** is running and healthy before asserting on flow behaviour — checking only that infrastructure is reachable (broker up, DB accepts connections) is **not sufficient**
   - Include a readiness/health check with a reasonable timeout and a clear error message when the app is unreachable
   - Distinguish between "infrastructure not available" (skip gracefully) and "app not started" (fail with clear instructions)

### Section 6 — Local Simulation Setup *(optional — only if Step 2C identified dependencies)*

```markdown
## Local Simulation Setup

### Run Mode
- [ ] Mode A: App on developer's host + separately managed dependencies (env vars use host-reachable addresses)
- [ ] Mode B: All components run together in a managed local environment (env vars use internal service addresses)
- [ ] Both — document env vars for each mode separately

### Dependencies & Local Substitutes
| Real Service | Local Substitute | Version / Config | Auth Override Needed |
|---|---|---|---|
| {service} | {substitute} | {version or image tag} | {yes/no — detail} |
```
